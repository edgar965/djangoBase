Wozu diese Seite da ist — und wie man sie benutzt

Ein zweites Modell taugt als Kritiker nicht, weil es mehr wüsste, sondern weil es die eigenen Schlüsse NICHT kennt. Wer seinen eigenen Code prüft, prüft ihn mit denselben Annahmen, mit denen er ihn geschrieben hat. Genau daran ist hier schon mehrfach ein Befund gescheitert, den sein Autor für sicher hielt.

So läuft ein Review:

  1. Einen Codebereich wählen (oder mehrere — jeder bekommt seinen eigenen Gesprächsverlauf).
  2. Die vorgeschlagenen Fragen stehen im Bereich; sie sind auf dessen typische Fehler gemünzt. Eigene Frage geht auch.
  3. Nachfassen, solange die Antwort allgemein bleibt. Die erste Antwort eines Modells ist oft eine Stilkritik — die zweite wird konkret, wenn man nach einem BELEG fragt: „In welcher Zeile? Was wäre die Eingabe, die das auslöst?"

Wann sich das lohnt: bevor eine Idee groß aufgezogen wird, besonders wenn man selbst überzeugt ist. Ein Einwand vor der Messung kostet Minuten, einer danach eine Nacht Rechenzeit.

Was ein Modell hier NICHT kann: Es sieht nur die Dateien des Bereichs, nicht den Lauf und nicht die Daten. Es kann eine These angreifen, aber keine Zahl bestätigen. Jede Aussage, die eine Zahl enthält, bleibt zu messen.

Bereiche pflegen — in den Projekt-Settings unter DJANGOBASE["review_bereiche"]: slug, name, dateien (Pfade ab Projektwurzel), hinweis (was dieser Code tut und woran er typischerweise scheitert) und fragen. Der hinweis ist der wichtigste Teil: Ohne ihn beurteilt das Modell Handelslogik wie Web-Code.

Noch kein Modell-Partner eingetragen

Diese Seite befragt ein zweites Modell zu eigenem Code — lokal über Ollama oder online über einen OpenAI-kompatiblen Endpunkt. Beides wird in den Projekt-Settings eingetragen:

DJANGOBASE = {
    ...
    "review_partner": [
        {"slug": "nemotron", "name": "Nemotron 550B", "ziel": "online",
         "modell": "nvidia/nemotron-3-ultra-550b-a55b"},
        {"slug": "gemma", "name": "Gemma (lokal)", "ziel": "lokal",
         "modell": "gemma4:26b-a4b-it-qat", "num_ctx": 32768},
    ],
    # Basis der Bereichs-Dateien (None -> BASE_DIR)
    "review_wurzel": str(REPO_DIR),
    "review_bereiche": [
        {"slug": "kern", "name": "Rechenkern",
         "dateien": ["paket/kern.py", "paket/modell.py"],
         "hinweis": "Was der Bereich tut und was das Modell wissen muss.",
         "fragen": ["Wo kippt die Rechnung, ohne dass es auffällt?"]},
    ],
}

Der Schlüssel für „online" gehört in eine Datei außerhalb des Projekts: ~/.sparring_key (eine Zeile) — nicht ins Repository und nicht in eine Kommandozeile, die in jedem Protokoll landet. Über DJANGOBASE["review_schluessel_datei"] änderbar.
